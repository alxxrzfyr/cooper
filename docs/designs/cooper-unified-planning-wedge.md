# Design: COOPER's trusted planning loop

## Problem statement

COOPER has the pieces of an AI-native planner, but they do not yet behave like one product. Ask,
Home, Calendar, badges, tasks, and connected providers calculate different partial versions of the
user's day. The visible result is a trust failure: generic answers, incomplete calendar counts, and
AI confirmations that are not clearly tied to committed application state.

The user should experience one promise:

> COOPER tells me what to do next from my real schedule, and every change it claims is visibly real.

## Demand evidence

The current evidence is strong problem conviction from the owner, not yet market validation:

- “That completely defeats the purpose of having an AI-native planning app.”
- “No fake confirmations.”
- Home should answer, “What do I need to know and do right now?”
- COOPER should feel “less like a calendar app with an AI chatbot attached.”

These statements identify a painful trust and coherence problem. They do not prove that other users
will adopt or pay for the solution. The first delivery should therefore optimize for proving the
trusted planning loop, not for finishing every possible planning surface.

## Status quo

- Ask sees local task summaries and anonymous busy intervals but does not consistently use one
  authoritative view of the day.
- Calendar merges local and external records in the browser.
- Navigation counts only COOPER-scheduled records.
- Home shows external events in its strip but chooses its recommendation from the local shortlist.
- Importance exists but does not affect ranking.
- Local writes usually persist correctly, but Ask has no complete mutation vocabulary or structured
  post-commit receipt.

The user must currently reconcile the system manually, which is exactly the work COOPER is meant to
remove.

## Target user and narrowest wedge

The initial user is one person who has local tasks plus at least one connected calendar and wants a
trustworthy answer to three questions:

1. What should I work on next?
2. What remains today?
3. Did COOPER actually save the change I requested?

The narrowest valuable release is not a full command-center redesign. It is a trusted planning loop:

```text
real commitments -> one planning snapshot -> specific recommendation
       ^                                           |
       |                                           v
visible committed state <- verified local mutation receipt
```

## Constraints

- `app.py` remains the only database writer.
- `brain.py` interprets and validates but never writes.
- External calendars remain read-only.
- Provider contents do not enter Gemini prompts.
- Manual/Form works without Gemini or connected providers.
- No new database table, dependency, queue, background process, or project-management model.
- Missing provider data is never treated as free time.

## Premises

1. Trust is the product bottleneck, not the number of available AI actions.
2. One derived planning snapshot is enough; copying external events into a new ledger is unnecessary
   until real usage proves otherwise.
3. Common planning questions should be calculated by COOPER and optionally phrased by AI, not
   calculated by the model.
4. Provider-aware counts, grounded recommendations, and verified mutation receipts will create a
   noticeably better product before a full Home redesign.
5. The product should block only decisions that require unavailable provider data; safe local reads
   and writes continue with a visible warning.

## Approaches considered

- **Patch each surface:** fastest initial diff, rejected because it preserves conflicting definitions
  of the user's day.
- **Shared derived planning snapshot:** chosen because it creates one interpretation without a new
  persistence or synchronization system.
- **Persisted unified event ledger:** rejected because it adds migrations, reconciliation lifecycle,
  and operational cost before the need is proven.

## Recommended approach

Use the shared planning snapshot, but deliver it in founder order rather than platform order.

### Release 1: Prove the trusted planning loop

1. Normalize and deduplicate commitments.
2. Produce one mixed-source count and availability model.
3. Make importance affect deadline-first ranking.
4. Ground the existing suggested Ask prompts in snapshot facts.
5. Return verified receipts for create and schedule actions.
6. Show provider incompleteness instead of inventing certainty.

This release should make the current product visibly more intelligent without redesigning every
surface.

### Release 2: Make Home the command center

After Release 1 is used with real schedules:

1. Build Now and Next from snapshot focus.
2. Build one mixed-source Today agenda.
3. Add At Risk and Upcoming without duplicating items.
4. Add local rescheduling with verified receipts.
5. Remove the remaining legacy frontend schedule calculations.

### Release 3: Remove compatibility fields

Backend and frontend deploy independently. First deploy the additive `planning` response, then the
snapshot-driven frontend. Remove legacy `shortlist`, `scheduled`, and `events` only after the hosted
frontend is verified. This is release hygiene, not product scope.

## Success criteria

The first release succeeds when, for seven days of real use:

- the calendar badge and visible day commitments agree every time;
- the three core Ask questions name real work and external busy time rather than giving generic
  advice;
- no AI success message disagrees with the resulting COOPER state;
- connected-provider failure produces an incomplete warning and no invented free block;
- the owner can answer “what should I do next?” without opening another calendar;
- every mismatch is recorded as a product bug, not dismissed as an AI-quality issue.

This can be validated with a small manual trust log. New analytics infrastructure is unnecessary.

## Open questions

- Demand beyond the owner remains unproven. Do not infer product-market fit from architectural
  correctness.
- Cross-provider exact-signature deduplication must be tested against real calendars before adding
  fuzzy matching.
- Provider latency should be measured before adding caching or persistence.

## Dependencies

- Existing Google and iCloud read paths.
- Existing local item model, ranking, placement, and source-health behavior.
- Existing authenticated `/api/today` and `/api/say` flows.
- Existing browser-configured Gemini key and request-scoped Brain behavior.

## The assignment

Ship Release 1 behind the existing product surfaces, then use COOPER with a real mixed-source
schedule for seven consecutive days. Record every incorrect count, generic answer, unavailable-time
mistake, and unverified mutation. Do not begin the full Home redesign until this loop is trustworthy.

## What I noticed about how you think

- You kept returning to “Did the AI actually create that?” That is the correct product question:
  trust beats conversational polish.
- You said the goal is not to add more features. That is the right constraint for a codebase whose
  existing features are not yet sharing one truth.
- You described Calendar, Tasks, Home, Ask, integrations, and badges as interfaces into one system.
  That is the durable product model; the planning snapshot is only the implementation mechanism.
